# U CAFE Loyalty — контекст проекта

## Главная идея

Это **универсальная платформа лояльности** для разных заведений (кафе, магазинов и т.п.), а не приложение, сделанное специально под одно кафе.

U Cafe — просто первый магазин, который подключён к системе. **Нельзя** писать код вида `if (store === "U Cafe")` или любую другую логику, завязанную конкретно на один магазин. Название, логотип, цвета, меню, акции, cashback, порядок блоков на экране — всё это приходит от магазина через API (white-label).

## Роли — только ДВЕ

1. **CLIENT** — покупатель
2. **ADMIN** — управляет магазином

**Кассир — не отдельная роль.** Все действия по обслуживанию клиента (сканирование QR, покупка, начисление кешбэка) выполняются через ADMIN-интерфейс. Разделение прав внутри ADMIN (кассир/владелец) — отдельная задача на будущее, сейчас не делаем.

Backend — не роль, это техническая часть, работающая автоматически.

## CLIENT — функциональность

- **Регистрация**: телефон → SMS-код → имя → аккаунт. После регистрации автоматически создаётся персональный QR.
- **Мой QR**: не отображается постоянно. На главном экране — кнопка "Мой QR" (внизу по центру), открывает QR только по нажатию. Клиент показывает его администратору/кассиру при покупке.
- **Добавление магазина**: клиент вводит ID магазина → приложение подгружает конфигурацию именно этого магазина.
- **Интерфейс магазина**: после подключения клиент видит именно интерфейс этого магазина — название, логотип, цвет, cashback, кошелёк, акции, rewards, меню, отзывы, сообщения и другие включённые блоки.
- **Кошелёк**: отдельный баланс для каждого магазина (`Wallet = CLIENT + STORE`), балансы не смешиваются между разными кафе.
- **Cashback**: виртуальные бонусы, не реальные деньги. Процент задаёт сам магазин. Бонусами можно оплатить покупку — **без искусственного лимита** (если правила магазина позволяют — хоть 100% покупки бонусами).
- **Акции**: магазин сам решает, включать ли акции. Клиент не создаёт и не настраивает акции. Если активной акции нет — блок "Акции" **автоматически заменяется** блоком "Отзывы" (это конкретно fallback-поведение главного экрана, не общее правило).
- **Прогресс акции**: считается вручную администратором. У loyalty-системы нет доступа к кассе и составу покупки. После сканирования QR клиента ADMIN вручную указывает количество единиц, относящихся к акции (например "+2 кофе"). Система сама складывает прогресс. Если условие акции выполнено (например 8/8) — выдаётся reward, а **остаток переносится в новый цикл**, не сгорает.
- **Rewards**: отдельная сущность от бонусного кошелька. Получение reward НЕ списывает бонусы. У reward есть статус использован/не использован.
- **История**: покупки, начисления кешбэка, списания бонусов, rewards и их использование.
- **Меню**: находится внутри главного экрана, не отдельным сложным разделом.
- **Главный экран**: один экран, который клиент листает вниз. Состоит из блоков (кошелёк, cashback, прогресс, акции/отзывы, меню, новинки, сообщения и т.д.). **ADMIN задаёт порядок этих блоков** через свою панель — клиент ничего не настраивает, просто видит готовую конфигурацию.
- **Сообщения**: ADMIN может отправить конкретному клиенту личное сообщение внутри приложения.

## ADMIN — функциональность

- Управление магазинами
- Управление клиентами
- Настройка cashback
- Создание и управление акциями
- Управление rewards
- Работа с покупками (после сканирования QR клиента)
- Статистика
- Управление меню
- Настройка блоков главного экрана и их порядка
- Отправка сообщений клиентам
- Работа с отзывами
- Включение/выключение любых возможностей магазина по своему усмотрению

## Multi-store — обязательное требование

Один CLIENT может подключить несколько магазинов. У каждого магазина — свой баланс клиента, свой cashback, свои акции, rewards, история, меню, дизайн, сообщения и структура главного экрана. **Данные разных магазинов никогда не смешиваются.**

## Backend — источник истины

Все критичные расчёты (cashback, баланс, прогресс акции, rewards, списание бонусов) подтверждаются и вычисляются **только на backend**. Frontend ничего из этого не считает самостоятельно — только отображает то, что пришло с сервера.

## Технологии

- **Client**: Angular
- **Backend**: Node.js + TypeScript + Express
- **DB**: PostgreSQL

Сначала делаем полноценное веб-приложение. После завершения — упаковка через **Capacitor** в Android/iOS (не отдельные нативные приложения с нуля).

## UX-принцип

Приложение не должно быть перегружено экранами. Клиент открывает приложение и сразу понимает: где баланс, что можно получить, какой прогресс, где меню, где акции, где кнопка "Мой QR". Простой интерфейс снаружи — сложная логика внутри.

## Текущее состояние кода (на момент последнего анализа)

✅ **Уже реализовано и работает:**
- Схема БД: `users`, `stores`, `user_stores`, `wallets` (по паре user+store), `wallet_transactions`, `purchases`
- Расчёт cashback в `createPurchase` — через `BigInt`/basis points (без float для денег), в одной SQL-транзакции с блокировкой строки (`FOR UPDATE`) для защиты от гонки при параллельных запросах
- QR: токен генерируется один раз через `crypto.randomBytes`, не пересоздаётся зря
- **SMS-верификация регистрации/входа** (реализована в этом чате):
  - `POST /auth/request-code { phone }` — отправляет код, в DEV-режиме возвращает его в ответе как `devCode` (реального SMS-провайдера пока нет — заглушка, `smsService.ts` написан так, что провайдер подключается заменой одного файла)
  - `POST /auth/verify-code { phone, code, name? }` — проверяет код (лимит 5 попыток, TTL 5 минут, защита от спама повторной отправки раз в 60 сек), создаёт/логинит пользователя, выдаёт JWT
  - Формат телефона — строго `+998XXXXXXXXX` (Узбекистан)
  - Таблица `verification_codes` хранит только хеш кода, не сырой код

❌ **Не реализовано / предстоит:**
- Оплата бонусами (списание баланса, `type: 'spend'` — тип есть в constraint, но нет endpoint'а)
- Акции (`promotions`) и прогресс акций (`promotion_progress`) — таблиц нет вообще
- Rewards — сущности нет
- Отзывы — сущности нет
- Сообщения от магазина клиенту
- Конфигурация и порядок блоков главного экрана
- Весь Angular-фронтенд клиента (сейчас есть только заготовка `dashboard`, реальных экранов под функционал нет)
- Разделение прав внутри ADMIN (владелец/кассир) — отдельная задача на будущее
- Отдельный сайт админ-панели — тоже отдельная задача на будущее, сейчас фокус только на клиентском приложении

## Правило работы над проектом

- Ничего не добавлять и не менять в архитектуре самовольно
- Перед любым изменением — сначала изучить существующий код, не считать что-то готовым только потому что оно описано в ТЗ
- Один блок функциональности доводится до полностью рабочего состояния, потом переходим к следующему
- Если есть сомнение по архитектуре — сначала объяснить проблему и предложить варианты, не решать самовольно
